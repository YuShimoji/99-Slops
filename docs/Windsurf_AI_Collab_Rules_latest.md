# GLITCH-WORKER AI協調開発ルール

本書は、ツール名に依存しない project-local の実行契約です。監修AI、実装AI、人間ディレクターの全員に適用します。汎用の `shared-workflows/`、旧 `Windsurf_AI_Collab_Rules_v1.1.md` / `v2.0.md` と競合するときは、`AGENTS.md` と本書を優先します。

## この運用が解消する摩擦

| 以前の構造 | 起きていたこと | 今後の原則 |
|---|---|---|
| 1 micro-task = 1 Issue = 1 Prompt | 指示と確認が細切れになり、成果へ到達する前に往復が増える | 1 Prompt = 1 Outcome Slice |
| 仮定数やUnity不在を一律停止条件にする | 可逆な判断でも安全側に倒れて停止する | 件数ではなく可逆性と影響で判断する |
| AI_CONTEXT / MISSION_LOG / HANDOVER / MILESTONE / RESUMEを都度同期 | どれかが必ず古くなり、読む入口で現在地が変わる | 動的な現在地は `WORKFLOW_STATE_SSOT.md` だけ |
| 完成後に見た目を初めて確認する | 大きな修正から微修正の沼へ入る | 高コスト制作前に粗い方向を選ぶ |
| 実装方式の3案だけを「創造性」とする | UI、色、フォント、演出、言語、隣接コンテンツが探索されない | 適切な節目で体験・表現・展開を横断して探索する |

## 権限と正本

1. ゲーム仕様は `docs/spec/GDD1.0.md`。AIは改変しない。
2. 不変の技術・スコープ・停止条件はルート `AGENTS.md`。
3. 現在地、Active Slice、検証結果、Human Authority は `docs/WORKFLOW_STATE_SSOT.md`。
4. Roadmapは将来範囲と依存の地図であり、進捗正本ではない。
5. Task / Report / Prompt はその時点の契約または証跡であり、現在地を重複保持しない。

「Phase」だけでは、ゲーム開発段階とAIワークフロー段階が混ざります。報告では必ず `Product milestone`、`Current slice`、`Verification gate` の軸を分けます。

## 作業単位は Outcome Slice

Outcome Slice は、プレイヤーまたは開発判断にとって意味があり、完了後に一まとまりで評価できる成果状態です。ファイル数や工程数では分割しません。通常は、主実装に必要な関連修正、限定テスト、Scene配線、証跡、現在地更新までを一つに含めます。

次の場合だけ分割します。

- 人間が選ぶ方向によって成果が大きく変わる。
- 依存追加、仕様変更、破壊的操作など、別権限が必要になる。
- 独立して価値を出せる成果同士で、片方の失敗がもう片方を巻き込む。

「クラスを1個追加」「Reportだけ作る」「Promptだけ後追いで作る」は、それ自体がユーザー価値を持たない限りOutcome Sliceにしません。

## 監修AIが渡す Execution Brief

監修AIは、細かな実装手順ではなく成果責任を渡します。コードと現在地を確認してから、次の形で一枚に収めます。

```text
Execution Brief: <成果名>

Outcome:
- 完了後に誰が何をできるようになるか

Why now:
- 現在のボトルネックと、この成果が次を開く理由

Fixed decisions:
- GDD、人間が選択済みの方向、互換性制約

Authority:
- 関連修正、局所リファクタ、限定テスト、Scene配線、状態同期まで実施可

Non-goals:
- 今回は増やさない機能・表現

Acceptance:
- 観測可能な動作と必要な証跡

First-look gate:
- なし / 高コスト制作前に一度だけ確認する地点

Stop only if:
- この成果固有で人間判断が必要になる条件

Closeout:
- WORKFLOW_STATE_SSOT更新、検証結果、次の入口
```

監修AIは次を守ります。

- 共通ルール全文をPromptへ複製せず、正本へリンクする。
- `<未設定>`、存在しないパス、観測不能なAcceptanceを残したBriefを発行しない。
- 可逆な細部を先回りして決めすぎない。実装AIに裁量を渡す。
- 単なる保守案だけでなく、前進・探索・摩擦除去の視点を持つ。
- 人間の方向選択が不要なら「途中確認なしでCloseoutまで進める」と明記する。

## 実装AIの連続実行

| 段階 | 行うこと | 中断点 |
|---|---|---|
| Orient | Git差分、GDD制約、現在地、実装実態を短く照合する | BriefとGDDがmaterially競合するときだけ |
| Deliver | 主実装と成立に必要な隣接修正をまとめて行う | 下記の停止条件だけ |
| Verify | リスクに比例した最小十分な検証をまとめて行う | 失敗時は原因を切り分け、直せる範囲は直す |
| Close | 状態正本を一度更新し、意味・検証・不確実性・次の入口を報告する | 次Sliceの優先順位は人間が選べる |

実装AIは、Outcome達成に必要なら次を追加確認なしで行えます。

- 読み取り、検索、差分確認、ビルド、限定テスト、静的検査。
- 同じ不具合原因に属する関連修正と、変更箇所の小さな整理。
- 既存テストの修正・追加、Scene参照の整合、ドキュメントの事実同期。
- 可逆でGDD内に収まる既定値の選択。選んだ理由はCloseoutに残す。

## 本当に停止する条件

次のいずれかに該当するときだけ、人間へ選択肢を提示して停止します。

1. 履歴書換え、追跡資産の削除、大量上書きなど破壊的・復旧困難な操作。
2. Package / 外部依存の追加、メジャー更新、プロジェクトルート構成変更。
3. DB、認証、課金、外部API契約、公開・配布先の変更。
4. GDDとの仕様競合、またはMVP外へ materially 拡張する判断。
5. レイアウト、アート、演出、コンテンツ量など、後戻りコストが高い方向が未選択。
6. ユーザー作成アセットを失う可能性、または当初Outcomeと別物になるスコープ拡張。

「仮定が3件ある」「Unityを今すぐ起動できない」「手動確認が一部残る」は、それだけでは停止条件ではありません。代替検証を行い、未検証部分を `VALIDATING` としてまとめて回収します。

## 検証はリスク比例

| 変更 | その場で必要な検証 | 節目で追加する検証 |
|---|---|---|
| Markdown / 状態更新 | リンク、差分、整合性、`git diff --check` | なし |
| 純粋C#ロジック | コンパイル、対象ロジックのテストまたはコード確認 | Unity import / 関連回帰 |
| Unity Scene / Prefab / SerializeField | YAML・GUID・参照確認、可能ならUnity import | PlayMode smoke |
| 物理、入力、カメラ、UI体験 | コンパイルと対象Scene smoke | 実際の操作、スクリーンショットまたは短い動画 |
| Package / Unity更新 | restore、full rebuild、Unity batch import | 主要Scene回帰 |

すべての実装に一律でEditMode + PlayMode + full buildを要求しません。変更に必要な検証だけを行い、マイルストーン境界でまとめて広い回帰を実施します。検証できなかった事実は隠さず、実装全体を凍結する代わりに検証債務として次のGateへ載せます。

## 状態と証跡を分ける

新しい作業の進行状態は次の5語だけを使います。

| 状態 | 意味 |
|---|---|
| `READY` | Outcome、権限、Acceptanceが揃い、すぐ実行できる |
| `ACTIVE` | 実装または修正中 |
| `BLOCKED` | 人間判断・外部状態・新権限・未充足の前提がなければ進めない |
| `VALIDATING` | 実装は存在するが、Acceptanceの証跡が未完 |
| `DONE` | Acceptanceが必要な証跡で確認された |

実装到達度と検証深度は別に書きます。たとえば `delivery: implemented / verification: playmode_pending` とし、`COMPLETED_CORE` のような一語へ混ぜません。

- `WORKFLOW_STATE_SSOT.md` はCurrent slice、最終検証、Human Authority、次の一手が変わったCloseout時だけ更新する。
- 作業開始時やコマンドごとに複数の状態ファイルを更新しない。
- Reportは実行時点の証跡として凍結し、最新状態のために追記し続けない。
- Task / Issueは複数セッション、複数担当、外部調整が必要なOutcomeにだけ作る。
- Git履歴で分かる作業のために後追いPromptや長い報告ファイルを作らない。

## 創造的な方向確認

主観的で手戻りが大きい作業には、次の順序を使います。

1. **Direction**: レイアウト、色、フォント、カメラ、アニメーション、言語、トーンのうち重要な軸を2〜3方向に分ける。
2. **Cheap prototype**: ワイヤーフレーム、灰箱、一画面、一演出、短い文例など安価な形で見せる。
3. **Human choice**: 狙い、利得、コスト、撤退条件を比較し、一度だけ方向を選ぶ。
4. **Delivery**: 選択済み方向を一気に実装する。
5. **First look**: 量産前に必要なら一度だけ確認し、その後はAcceptanceまで進める。

同じ成果で微修正が2巡したら、3巡目へ入る前に目的と選択軸を再確認します。完成品を少しずつ直し続けるのではなく、方向の取り違えかAcceptance不足かを切り分けます。

各SliceのClose前には短い Exploration Pulse を行います。外部化する提案は最大2件とし、次の観点から「今なら低コストで効くもの」だけを出します。

- プレイヤーの手触りと行動。
- 色、フォント、レイアウト、カメラ、アニメーション、音。
- 言語対応、アクセシビリティ、入力表示。
- 既存システムから伸ばせるコンテンツ。
- 繰り返した手作業の自動化、または不要工程の削除。

未採用案はRoadmapへ混ぜず、必要なら `docs/spec/SKILL_IDEAS.md` など明示されたIdea Poolへ置きます。

## Closeoutと次の選択肢

完了報告は、ファイルを開かなくても意味が伝わる自然文にします。何を変え、なぜ体験・workflow・意思決定に効くか、実際に何を検証し、何がまだ不確実かをつなげます。複数の変更・選択肢・残作業がある場合は比較表を使います。

次の入口は2〜4件に絞り、同じ種類の微修正を並べません。たとえば次の異なるボトルネックから選び、完了すると何が可能になるかを書きます。

- **Advance**: ゲームの主線を前進させる。
- **Verify**: 未確定の動作を証拠付きで確定する。
- **Audit**: 仕様・実装・状態のずれを解消する。
- **Excise**: 摩擦を生む重複・不要工程を取り除く。
- **Explore**: 安価な試作で新しい方向を比較可能にする。

## リポジトリ外から見える現在地

GitHubのルート `README.md` を安定した入口とし、そこから `WORKFLOW_STATE_SSOT.md` を直接読めるようにします。WikiやGitHub Pagesは第二の手書き正本にしません。

- Pagesを使う場合は、default branchのMarkdownから自動生成する。
- Wikiを使う場合は入口と用語集に限定するか、CIでミラーし、手動で状態を複製しない。
- 体験が変わるSliceでは、最新スクリーンショットまたは短い動画をTask/PRからリンクする。
- 公開ページの更新漏れは「担当者の注意力」ではなく、同じソースから生成する仕組みで防ぐ。

## 停滞時の回復

- 保守・テスト・文書整備が2 Slice続いたら、GDD上の成果状態へ戻る最短経路を再計算する。
- 手動確認を3回以上個別に求めそうなら、一つのVerify Batchへまとめる。
- 選択肢が保守案に偏ったら、逆算法・隣接機会・摩擦削除の少なくとも一つから再生成する。
- Promptが細切れになったら、同じAcceptanceに従属する作業を一つのExecution Briefへ再結合する。
- 現在地の記述が競合したら、コードと検証証跡を確認し `WORKFLOW_STATE_SSOT.md` だけを直す。他の履歴文書へ同じ文章を複製しない。

旧ルールと汎用submoduleは参照資料として保持しますが、その更新を自動的に採用しません。submodule更新は依存更新として差分と互換性を確認し、このproject-local契約を弱めない場合だけ親リポジトリのポインタを更新します。

## 旧自動化の扱い

2026-07-10の監査では、汎用スクリプトとこのリポジトリのTask / Report書式が一致していませんでした。

| 自動化 | 不一致 | 当面の扱い |
|---|---|---|
| `worker-dispatch.js` | `Tier:` / `## Objective` / `## DoD` を期待するが、実Taskは別見出し | 生成Promptを実行契約として信用しない。`<未設定>`を含むPromptは拒否する |
| `todo-sync.js` | 現行Status見出しを認識せず、OPENのTASK_025を未完了として検出しない | 未完了判定に使わない |
| `orchestrator-audit.js` | 同じ書式差で不整合を見逃しても `OK` になりうる | 完了ゲートに使わない |
| `finalize-phase.js` | Report命名とTaskの`Report:`欄が実成果物と不一致 | HANDOVER等の自動同期を前提にしない |
| 生成Promptの参照パス | 実体は `shared-workflows/` だが `.shared-workflows/` を指す例がある | 動的に存在確認し、誤パスを引き継がない |

これらを直す作業はゲーム開発の主線ではありません。再利用する時だけ、現行Task fixtureを使ったparser testを先に追加し、「未完了を確実に検出する」ことを確認してから復帰させます。それまではGit差分、コード、`WORKFLOW_STATE_SSOT.md`、実検証を人間とAIの判断根拠にします。
